# Visual Plan

Produce a durable local bundle instead of a chat-only plan:

```text
plans/<slug>/
  index.md
  presentation.mdx
  artifact.html
  assets/
```

`index.md` is canonical and must remain useful in Obsidian and GitHub.
`presentation.mdx` is a richer review layer. `artifact.html` is the portable,
self-contained reading view generated by `mdx-publish`.

## Workflow

1. Inspect the real repository, branch, source files, tests, and local
   instructions. Planning is read-only unless the user separately authorizes
   implementation.
2. State the outcome, scope, explicit non-goals, and any assumptions that could
   change the design.
3. Ground the plan in actual files and symbols. Separate verified facts from
   inference.
4. Decide hard-to-reverse boundaries first: public interfaces, identifiers,
   data shape, ownership, security, migration, and rollback.
5. Write `index.md` with:
   - outcome and concrete example
   - current state and proposed state
   - decisions and rejected alternatives
   - architecture or workflow
   - affected file map
   - ordered implementation slices with dependencies
   - verification, rollout, rollback, and risks
   - unresolved questions with recommended defaults
6. Create `presentation.mdx` from the same facts. Use `Flow`, `Comparison`,
   `Steps`, `FileTree`, `DataModel`, `ApiEndpoint`, and `Disclosure` only when
   they make the relationship easier to review.
7. Read `~/.agents/skills/mdx-publish/references/components.md`, then run:

```sh
npm --prefix ~/.agents/skills/mdx-publish run check -- "$PWD/plans/<slug>"
npm --prefix ~/.agents/skills/mdx-publish run build -- "$PWD/plans/<slug>"
```

8. Open `artifact.html` locally and inspect desktop and narrow-width layouts.
   Ask for approval before implementation when the plan is the requested gate.

Use `tasteful-html-artifacts` instead when a UI plan needs a bespoke interactive
prototype or precise wireframe rather than this document-oriented component set.

## Quality bar

- Prefer one committed recommendation over an unexplained menu of choices.
- Make every step independently verifiable and name what it reuses.
- Keep diagrams semantic; do not add a visual for a one-step relationship.
- Do not invent code, metrics, file paths, or product states.
- Make the artifact standalone: a reader should not need the originating chat.
